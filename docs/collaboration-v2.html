Activation fixv2 proposal

A turn can end. Responsibility cannot disappear. This plan adds native addresses, one-sided invitations, scoped permission supervision, and durable work ownership across multiple sessions.

The examples explain proposed behavior. They do not contact or control a session.

Different rhythms.
The same responsibility model.

The coordinator owns the outcome. Each work item has one owner, a next action, and a completion condition. Parallel work means separate items with explicit boundaries.

The invariant

Every unfinished active goal has fresh execution evidence, a durable wake, or a named blocker.

An active database label is not proof of progress. Before ending a turn with runnable work, atomically record the checkpoint, next owned action, and a wake event or due time. A committed handoff, named dependency, or explicit pause can instead explain the next obligation.
State machines

Separate the turn from the work.

Session availability is an observation. Work and goals are durable commitments. None of these states should be inferred from a model’s final message.

The goal

The user’s outcome and acceptance criteria, with one accountable coordinator.

draft→active→verifying→completed
Verification fails → active. Record what still needs work.
Blocked names a dependency, responsible party, and recovery condition. Resolving it returns the goal to active.
Paused means intentionally suspended, including a budget decision. Resume requires the user’s authorization.
Cancelled is explicit. It never means achieved.

A work item

A bounded deliverable, its owner, dependencies, checkpoint, and evidence.

ready→active→submitted→accepted
Changes requested → active. A submission is an attempt; acceptance validates the result.
Blocked affects this item. Independent ready items can continue.
Outcome unknown requires reconciliation. A timeout does not authorize repeating a command.
Reviews pin a revision. Accepting revision A does not approve a later revision B.

Idle can be correct. Both models may wait while a benchmark runs. The ledger must still name its owner, the expected output, and the next check. If both clients are gone, work stays unresolved until a receiver or an authorized helper returns.

Ownership transfer

A handoff has a commit point.

“I sent it to Claude” is not a transfer. The current owner stays accountable until the target is ready and the ledger commits the new owner.

Checkpoint

Codex records evidence and in-flight effects, then quiesces the transferred item.

Offer

Name Claude, the exact checkpoint, ownership epoch, and deadline.

Ready ACK

Claude accepts that exact item and checkpoint. Ownership has not changed yet.

Commit

A guarded transaction changes the owner once and schedules the continuation.

Codex accountable · checkpoint → offer → ACK
Claude accountable · commit → continue

Codex can keep working on other items throughout. A lost acknowledgement is resolved by reading the committed ledger. This guarantees one recorded owner; it cannot fence an already-running external command without action-layer enforcement.

Consume

Atomically consume the matching decision and respond to the original hook. A changed or expired request needs a new decision.

The blocked Claude turn does not need to read a chat reply. Approval returns directly through its waiting hook. Timeout, offline supervisor, or unsupported prompts preserve the normal human flow. Native deny rules and provider controls remain in force; sandbox network prompts do not fire this hook.

Reject circular supervisor dependencies. An agent cannot grant itself broader authority or use another session to bypass its own restrictions. Nothing in this document enables a live permission grant. Claude PermissionRequest reference

Failure cases

Keep uncertainty explicit.

Most collaboration bugs happen between “sent,” “seen,” “accepted,” and “done.” Each boundary needs its own durable fact.

What stays true

Next action

Wake on useful events. New assignment, committed handoff, completed dependency, review result, live permission request, or a due checkpoint. Coalesce updates. Receipts and progress chatter do not wake models. An overdue item gets a bounded recovery nudge, then backoff and a visible blocker.

Comparable work · primary sources

Borrow the mechanisms,
keep the existing sessions.

These projects solve useful parts of the problem. None by itself establishes this exact two-session activation, permission, and completion contract.

MCP Agent Mail ↗

Borrow separate read receipts, acknowledgements, contact grants, and advisory file reservations. Receiving a message does not mean accepting work.

Beads ↗

Borrow durable dependencies, ready work, and atomic ownership claims. A work ledger complements the transport; it does not replace it.

A2A task lifecycle ↗

Borrow the distinction between messages, tasks, artifacts, interruption, and terminal outcomes. A conversation can contain many pieces of work.

agent-channel ↗

Borrow durable cursors and event-driven receive. Its documented host wake constraints reinforce the need for explicit adapter capabilities.

agent-mail ↗

Compare a durable local mailbox and optional liveness helper. Notification and persistence are distinct concerns; host integration still matters.

Ruflo / claude-flow ↗

Compare persisted workflow coordination and execution adapters. Its wider orchestration harness is a reference, not a demonstrated attachment to these existing terminals.
